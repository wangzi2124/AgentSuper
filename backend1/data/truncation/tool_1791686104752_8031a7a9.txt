1: # Knowledge Base System — RAG + AI Agent
2: 
3: 基于 RAG（检索增强生成）的知识库 AI 问答系统，支持文档上传、向量检索、多模型对话、Skills 和 Plugins 动态扩展。
4: 
5: ---
6: 
7: ## 功能
8: 
9: | 功能 | 说明 |
10: |------|------|
11: | **智能问答** | 上传文档后，通过 RAG 检索相关内容，结合 LLM 生成精准回答 |
12: | **多 Agent 编排** | Supervisor Agent 自动分析用户意图，路由到最合适的子 Agent 并行处理，支持多 Agent 流式响应 |
13: | **多模型支持** | 前端下拉菜单切换 DeepSeek V3 / R1、OpenAI GPT-4o / 4o-mini |
14: | **文档管理** | 支持 TXT / MD / PDF 上传，自动**章节感知分块**、向量化存储到 ChromaDB |
15: | **混合检索** | 向量检索 + BM25 关键词检索融合（RRF 排序），精确匹配与语义搜索兼顾 |
16: | **结构化章节检索** | 用户问题命中章节关键词（如"第一章"）时，**跳过向量检索**，直接查章节元数据表返回精确结果 |
17: | **父子文档结构** | 分块时自动生成父文档（章节标题+摘要）和子文档（正文块），检索子文档时携带父文档标题注入 LLM 上下文 |
18: | **中文支持** | 内置 `BAAI/bge-small-zh-v1.5` 中文嵌入模型，准确理解中文语义 |
19: | **上传进度** | 上传过程实时显示进度条（0-100%）及阶段描述（上传→分块→嵌入→入库） |
20: | **多轮对话** | 自动生成 conversation_id，支持同一会话内的上下文连续对话 |
21: | **会话隔离** | 每个会话独立消息存储，切换会话时消息互不干扰，后台流式请求继续运行 |
22: | **会话持久化** | IndexedDB 本地缓存 + 服务器 SQLite 双重持久化，页面刷新/SSE 中断不丢失消息（含 DataCloneError 修复：JSON 序列化剥离不可克隆值） |
23: | **会话管理系统** | 归一化会话库：用户/项目/工作区三级隔离、子会话树与 fork、上下文纪元、压缩基线持久化、消息撤销（revert）、AgentBus 任务自动登记为子会话 |
24: | **错误重试机制** | 三层重试架构：litellm 内置重试 → AgentBus 事件循环自愈 → 前端自动重试倒计时 + 手动重试按钮 |
25: | **并发控制** | 后端全局 Semaphore 限制同时运行的 Agent 任务数（`MAX_CONCURRENT_AGENTS` 默认 4），超出自动排队，前端实时显示排队/流式状态；session.db 使用 SQLite 连接池（WAL + busy_timeout），避免高并发连接反复开关 |
26: | **Skills（技能）** | Markdown 文件定义技能，动态加载，可在 Web 界面启用/禁用 |
27: | **Plugins（插件）** | Python 文件定义 tool_* 函数（如搜索、天气、生成文档），Agent 按需调用 |
28: | **HTTP 客户端** | Agent 可直接发起 HTTP 请求测试 API 接口（GET/POST/PUT/DELETE），支持自定义 headers 和 body |
29: | **Vector DB 开关** | 用户可在聊天界面手动控制是否启用向量库检索，关闭后 Agent 仅凭自身知识回答 |
30: | **生成文件管理** | Agent 创建的文档（.docx/.pdf/.xlsx/.pptx）可在独立页面查看、搜索、下载和删除，PDF 支持中文显示 |
31: | **本地 Embedding** | 使用 sentence-transformers 本地运行，通过 ModelScope 下载模型 |
32: | **检索重排序** | Cross-encoder 对检索结果重打分（top-3），显著提升回答精度 |
33: | **上下文管理** | tiktoken 精确 token 计数 + 上下文预算控制 + 工具输出智能边界/回溯清理 + 工具结果去重，防止 context 膨胀 |
34: | **对话持久化** | SQLite 存储对话历史，服务重启不丢失 |
35: | **来源引用** | 回答时标注检索到的文档来源及相似度分数 |
36: | **系统监控** | 请求级日志（方法/路径/状态/耗时）+ LLM 调用统计（模型/token/耗时/工具轮数），Web 页面可视化展示 |
37: | **消息滚动** | 聊天消息列表智能自动滚动（靠近底部才跟随，`isTrusted` 用户手势优先，用户上翻不被打断）；上翻浏览时右下角浮现「回到底部」悬浮按钮，点击平滑回底并恢复自动跟随 |
38: | **权限系统** | AI Agent 写外部路径时前端弹窗审批，支持白名单持久化；可写工作目录由前端「工作目录」面板配置（运行时生效、持久化、免重启），`EXTERNAL_PATH_DEFAULT` 控制外部路径默认策略、审批超时（`PERMISSION_APPROVAL_TIMEOUT`）可配置，总线路径无可解释拒绝而非静默失败；**Shell 重定向目标权限检查**：`>`、`>>`、`2>`、`2>>`、`&>` 写入的外部文件经过权限检查 |
39: | **任务执行引擎** | 参考 OpenCode 双层循环架构，任务持续执行直到完成，支持上下文压缩和最大步数限制 |
40: | **执行循环护栏** | `MAX_STEPS`（默认 40）最后轮注入收尾提示并禁用工具，强制"已完成/未完成/下一步"结构化总结；Doom-loop 检测（连续相同工具调用 ≥3 轮）注入策略变更提示，升级到上限后强制收尾 |
41: | **任务完成判断** | 读取 `finish_reason` 归一化为 OpenCode 六值语义，仅 `tool-calls` 维持工具循环，`length` 追加截断提示、`content-filter` 转为可解释错误 |
42: | **长任务不截断** | 输出上限 `LLM_MAX_TOKENS`（默认 16384）可配置；系统提示强制长内容（>500 字）写入文件、回复只留摘要，避免单轮输出触发截断（对齐 OpenCode 长任务机制） |
43: | **子代理超时分级** | 工具密集型子 Agent（如 code）使用更长等待（`SUB_AGENT_TIMEOUT_EXTENDED` 默认 300s）；子 Agent 仍活跃时自动宽限续期；失败时结构化回传已完成步骤 + 失败原因 + 建议 |
44: | **上下文压缩** | 消息超阈值（自动 = 可用预算的 60%，默认 ≈ 91K）时将旧消息压缩为锚定式结构化 checkpoint，保留最近 N 轮工具上下文 |
45: | **共享记忆持久化** | Agent 记忆（短期事实/偏好）持久化到 `data/agent_memory.json`，set/delete/clear 即时落盘（可异步去抖），重启不丢失；主 Agent 可通过 `tool_memory_set/get/search` 主动记忆/回忆/检索 |
46: | **SSRF 防护** | 所有出站 HTTP（`http_client` 插件、`tool_execute` 中的 curl/wget/ssh 等命令）经 `check_url`/`_ssrf_check_command` 校验，拦截内网/回环/链路本地/元数据地址及解析到它们的域名；`SSRF_ALLOW_INTERNAL=true` 可跳过（本地调试） |
47: | **用户身份签名** | 可选 `AUTH_TOKEN_SECRET`：trust-on-first-use 注册 → 服务端仅存 HMAC 哈希 → 颁发签名 token（`base64(uid).base64(exp).hmac`）；中间件强制每个 `/api/*` 请求携带 `X-User-Id` + `X-Auth-Token`，未配置时全部关闭（默认本地行为） |
48: | **多 Agent 工具链** | `code`/`web_search` 子 Agent 使用 LLM 工具调用循环（≤8 轮）+ 工作区文件系统工具（读写/编辑/搜索/执行），复用统一权限系统；外部路径经权限桥发事件并拒绝而非静默失败 |
49: | **文件附件** | 聊天输入框拖拽/粘贴/选择上传附件（图片/PDF/Word/Excel/TXT/MD 等），图片以多模态 `image_url` 直送 LLM，文档经 **LangChain 文档加载器**（`attachment_loader.py`：pypdf/python-docx/openpyxl）解析为文本上下文；附件随消息持久化（服务端 `data.files`），刷新/回放仍可回显 |
50: | **移动端响应式** | 统一手机端适配模块 `frontend/src/styles/mobile.css`（`main.ts` 引入，Vite 打包）：768/480px 断点，覆盖全部视图与组件 —— 侧栏抽屉化、触控友好按钮/输入、iOS 输入字号与 safe-area、聊天工具条换行、统计二列、弹窗底部 sheet/全屏、表格横滚等 |

54: ## 文档上传进度机制
55: 
56: 文档上传采用**异步任务 + 轮询**模式，前端实时显示量化进度：
57: 
58: | 阶段 | 进度 | 说明 |
59: |------|------|------|
60: | Uploading to server | 0-4% | 文件上传到服务器（XHR onprogress） |
61: | Queued for processing | 5% | 进入后台处理队列 |
62: | Saving file | 5% | 保存文件到磁盘 |
63: | Reading and chunking | 15% | 读取文件内容，章节感知分块（按 `第X章`/`Chapter X` 边界） |
64: | Generating embeddings | 25% | 开始生成嵌入向量 |
65: | Embedding (x/total chunks) | 25-90% | 逐批生成向量（最耗时的阶段，按 chunk 数精确量化） |
66: | Storing to vector database | 92% | 存入 ChromaDB |
67: | Complete | 100% | 处理完成，文档可用 |
68: 
69: **工作流程：**
70: 
71: 1. `POST /api/documents/upload` 立即返回 `{ task_id }`
72: 2. 后端 `TaskManager` 在后台依次执行：保存→分块→嵌入→入库
73: 3. 前端每 400ms 轮询 `GET /api/documents/tasks/{task_id}` 获取 `{ progress, stage }`
74: 4. 进度 100% 后，前端将文档加入列表
75: 
76: 实现路径：
77: - 后端：`backend/app/services/task_manager.py` — `TaskManager.process_document()`
78: - 前端：`frontend/src/api/documents.ts` — `uploadDocument()` → `pollTask()`

82: ## 中文支持与混合检索
83: 
84: ### 中文嵌入模型
85: 
86: 默认嵌入模型为 `BAAI/bge-small-zh-v1.5`，专门针对中文优化。在 `.env` 中可切换：
87: 
88: ```ini
89: EMBEDDING_MODEL=BAAI/bge-small-zh-v1.5    # 中文（推荐）
90: # EMBEDDING_MODEL=all-MiniLM-L6-v2        # 英文
91: ```
92: 
93: 模型通过 ModelScope 自动下载。
94: 
95: ### 分块机制
96: 
97: 上传文档后，`document_processor.py` 执行四步分块：
98: 
99: **① 章节检测** — 正则匹配 `第X章` / `Chapter X` / `CHAPTER X` 自动识别章节边界，无标记则整篇作为一章。
100: 
101: **② 父子文档结构** — 每章生成两类文档块：
102: 
103: | 类型 | 内容 | 用途 |
104: |------|------|------|
105: | **父文档** | 章节标题 + 前 300 字摘要（`is_parent: true`） | 章节概览检索，精确回答"第一章讲了什么" |
106: | **子文档** | 正文按 500 字滑动窗口切分（`is_parent: false`） | 细节检索，覆盖全文 |
107: 
108: **③ 滑动窗口分块** (`_chunk_text`)：
109: 
110: ```
111: CHUNK_SIZE=500     # 每块最大字数
112: CHUNK_OVERLAP=200  # 块间重叠 200 字，避免切句时断裂
113: ```
114: 
115: **④ 角色-台词锚点块** — 每章扫描对话模式（`张三说："..."` / `"..."张三说`），为每句台词生成独立锚点：
116: 
117: ```
118: text: 张三说：“你好吗？”
119: metadata: {is_dialogue: true, speaker: "张三", dialogue: "你好吗？"}
120: ```
121: 
122: 台词锚点块角色名+台词语义高度集中，搜索"张三说了什么"可直接命中。
123: 
124: 子文档保留 `chapter_title`/`chapter_number` 元数据，检索后强制注入父文档标题到 LLM 上下文。
125: 
126: 实现路径：`backend/app/rag/document_processor.py` — `process()` → `_split_chapters()` → `_chunk_text()` → `_extract_dialogues()`
127: 
128: ### 混合检索（Hybrid Search）
129: 
130: 结合两种检索方式：
131: 
132: | 方式 | 优势 | 适用场景 |
133: |------|------|----------|
134: | **向量检索** | 语义理解，找"意思相近" | 开放式问题、概括性查询 |
135: | **BM25 关键词** | 精确匹配，找"字面相同" | 章节名、人名、术语等事实查询 |
136: 
137: 两者通过 **RRF（Reciprocal Rank Fusion）** 算法融合，权重向量 0.7 + BM25 0.3。
138: 
139: **多路台词召回** — 检索时额外执行一路台词锚点搜索（`where={"is_dialogue": true}`），与主路径结果经 RRF 融合（台词权重 0.4），确保角色台词不被正文淹没。
140: 
141: 实现路径：
142: - BM25 索引：`backend/app/rag/bm25_index.py` — `BM25Index`
143: - 混合检索：`backend/app/rag/retriever.py` — `Retriever.invoke()`（含 RRF 融合 + 多路台词召回）
144: 
145: ### 结构化章节检索（两步走）
146: 
147: 解决"RAG 不能说出准确章节名"的工业级方案：
148: 
149: ```
150: 用户问 "第一章讲了什么"
151:   │
152:   ├─ intent.py: 正则匹配 → {chapter_number: 1}
153:   │     ↓
154:   ├─ 前置过滤：直接查 ChapterStore（SQLite 章节元数据表）
155:   │     ├─ 返回精确的 chapter_title + summary
156:   │     └─ 不再走向量检索
157:   │     ↓
158:   └─ LLM context 中携带 chapter_title + content
159:        → 准确回答，不再"猜章节名"
160: ```
161: 
162: **两步走策略**：
163: 
164: | 步骤 | 触发条件 | 行为 |
165: |------|----------|------|
166: | **1. 前置过滤** | 问题含 `第X章`/`Chapter X`/`关于...章节` 等关键词 | 关闭向量检索，精确查章节元数据表 |
167: | **2. 混合检索** | 无章节关键词 | 正常向量+BM25 混合检索，但结果自动携带父文档章节标题 |
168: 
169: **父子文档结构**：
170: 
171: 上传文档时，每个章节生成两种文档块：
172: - **父文档**：章节标题 + 前 300 字摘要 → 用于章节概览
173: - **子文档**：正文 1000 字分块 → 用于细节检索
174: 
175: 子文档 metadata 中保留 `chapter_title`，检索后强制注入父文档章节标题到 LLM Prompt。
176: 
177: 实现路径：
178: - 章节元数据表：`backend/app/rag/chapter_store.py` — `ChapterStore`
179: - 意图识别：`backend/app/rag/intent.py` — `detect_chapter_intent()`
180: - 父子分块：`backend/app/rag/document_processor.py` — `process()` 返回 `(chunks, chapter_metas)`
181: - 两步检索：`backend/app/rag/retriever.py` — `Retriever.invoke()` → `_chapter_lookup()` / `_enrich_with_parent()`

185: ### Vector DB 开关控制
186: 
187: 用户通过前端聊天界面的 **Vector DB** 开关手动控制是否启用知识库检索，系统不自动判断：
188: 
189: ```
190: 前端 Toggle（useVectorDb）
191:        │
192:        ▼
193: ChatRequest.use_vector_db: bool
194:        │
195:        ▼
196: AgentState.use_vector_db
197:        │
198:        ▼
199: _retrieve(state)
200:    │
201:    ├─ use_vector_db = false
202:    │     └─ return {context: [], sources: []}    ← 跳过向量库
203:    │
204:    └─ use_vector_db = true
205:          ├─ 向量检索 + BM25 混合检索
206:          └─ return {context, sources}             ← 注入知识库内容
207:               │
208:               ▼
209:          _generate(state)
210:               ├─ context 不为空 → system prompt 拼接知识库内容 → LLM 基于知识库回答
211:               └─ context 为空   → 纯 LLM system prompt（不携带知识库上下文）
212: ```
213: 
214: **关键点**：LLM **始终被调用**，区别只在于 prompt 中是否包含检索到的知识库内容。开关关闭后 Agent 仅凭模型自身知识回答（联网搜索等插件工具仍可用）。
215: 
216: 实现路径：`backend/app/agent/graph.py:64-78` — `_retrieve()` 检查 `state.get("use_vector_db", True)`

220: ## 技术栈
221: 
222: | 层 | 技术 |
223: |---|---|
224: | **后端框架** | Python 3.14+, FastAPI, Uvicorn |
225: | **AI Agent** | LangGraph（retrieve → rerank → generate 工作流）, LangChain |
226: | **LLM 调用** | LiteLLM（统一 DeepSeek / OpenAI / Ollama API） |
227: | **向量数据库** | ChromaDB（本地持久化，余弦相似度） |
228: | **文本嵌入** | sentence-transformers（all-MiniLM-L6-v2，通过 ModelScope 下载） |
229: | **检索重排序** | Cross-encoder（cross-encoder/ms-marco-MiniLM-L-6-v2，通过 ModelScope 下载） |
230: | **对话存储** | SQLite（本地持久化对话历史） |
231: | **前端框架** | Vue 3, TypeScript 5.7, Vite 6 |
232: | **状态管理** | Pinia |
233: | **路由** | Vue Router 4 |
234: | **文档解析** | LangChain 文档加载器：pypdf（PDF）、python-docx（Word）、openpyxl（Excel）、TextLoader（TXT/MD/JSON/CSV）——聊天附件与知识库上传共用 |
235: | **关键词检索** | BM25（rank_bm25）+ jieba 中文分词 |
236: | **文档生成** | python-docx（Word）、reportlab（PDF，微软雅黑字体）、openpyxl（Excel）三大生成引擎 |
237: | **互联网搜索** | Tavily API 实时搜索新闻、网页、财经信息 |
238: | **天气查询** | Open-Meteo API（免费，无需 key）获取天气实况和预报 |
239: | **生成文件管理** | Web 页面浏览/搜索/下载/删除 Agent 生成的 .docx/.pdf/.xlsx 文件 |
240: | **文本分块** | 父子文档分块（parent=章节摘要，child=正文块），按 `第X章`/`Chapter X` 边界 |
241: | **章节元数据** | SQLite 章节映射表（`ChapterStore`），支持章节号/标题精确查询 |
242: | **查询意图识别** | 正则匹配 `第X章`/`Chapter X`/`关于...章节`，自动选择检索策略 |

432: ### 可选：签名身份校验（`AUTH_TOKEN_SECRET`）
433: 
434: 在 `.env` 设置 `AUTH_TOKEN_SECRET` 后启用可信身份签名，防止伪造用户 ID：
435: 
436: 1. **Trust-on-first-use 注册**：前端生成随机 `user_id` + `device_secret`，`POST /api/auth/register` 上报，服务端仅存 HMAC 哈希（不存明文密钥）
437: 2. **签发 token**：`POST /api/auth/token` 返回签名 token（`base64(uid).base64(exp).hmac(uid:exp:reg_hash)`），有效期 `auth_token_ttl`（默认 30 天）
438: 3. **强制校验**：`AuthMiddleware` 要求每个 `/api/*` 请求携带 `X-User-Id` + `X-Auth-Token`（跳过 `/api/auth/*`、非 `/api` 路径、OPTIONS），校验签名与过期时间
439: 
440: | 文件 | 作用 |
441: |------|------|
442: | `backend/app/auth.py` | HMAC 哈希、token 签名/校验（`create_signed_token` / `verify_signed_token`）+ `AuthMiddleware`（未配置密钥时跳过） |
443: | `backend/app/api/auth.py` | `POST /api/auth/register` + `POST /api/auth/token` 路由（账户登录见 `backend/app/api/auth.py` 的 `/api/auth/account/*`，PBKDF2 哈希 + JWT） |
444: | `frontend/src/api/auth.ts` | `ensureAuth()` — 生成/读取 `user_id` + `device_secret`，自动注册并换取 token（`main.ts` 启动时调用） |
445: | `frontend/src/api/fetch.ts` | `addAuthHeaders()` 自动注入 `X-User-Id` + `X-Auth-Token`；`fetchWithTimeout` 封装自动带认证头 |
446: 
447: 后端通过 `_get_user_id(request)` 统一提取；启用签名校验后该函数同时验证 token，前端接口不变。

515: ## 智能体上下文管理
516: 
517: 每次对话请求通过 `conversation_id` 进行会话关联：
518: 
519: 1. **自动生成 ID**：首次对话不传 `conversation_id`，后端创建 `kind='multi-agent'` 会话并返回
520: 2. **历史加载**：`_session_history_for()` 传 `conversation_id` 则从 SQLite 恢复完整历史（正文优先取 `message_parts` 的 text part）
521: 3. **滑动窗口截断**：`_truncate_history()` 限制 16000 tokens，超出的最早消息被丢弃，插入 `[earlier history truncated]` 占位
522: 4. **摘要压缩（可选，分层）**：配置 `SUMMARIZATION_MODEL` 后在截断前先尝试用 LLM 压缩早期消息。旧消息按 `CHUNK_PAIRS`（默认 10 对）分批，每批独立压缩为子摘要，若子摘要合并后仍超阈值则递归合并，直到适应预算。保留最近的 `SUMMARIZATION_KEEP_MESSAGES`（默认 20）条完整消息。摘要失败时自动回退为截断。
523: 5. **持久化**：每次回答后，user/assistant 消息对追加写入 `data/session.db`（主会话 + `kind='task'` 子会话各一份，含 sources/steps/agents/tokens）
524: 
525: > 截断在 LLM 调用前发生，仅影响 prompt 传入的历史，不影响数据库中的完整记录。
526: 
527: 实现路径：`backend/app/api/chat.py` — `_session_history_for` / `_truncate_history` / `_persist_multi_agent`，`backend/app/middleware/summarization.py` — `HierarchicalSummarizationMiddleware`
528: 
529: ### 共享记忆持久化（Memory）
530: 
531: `MemoryManager`（`backend/app/agent/memory.py`）提供跨会话的短期记忆（Agent 主动记录的临时事实/偏好），未过期条目在 set/delete/clear 时写入 `settings.memory_persist_path`（默认 `data/agent_memory.json`），启动时重载，服务重启不丢失。`persist_path` 为构造函数注入，便于测试隔离。
532: 
533: **主 Agent 记忆工具**：主 RAG Agent（`graph.py`）注入共享 `MemoryManager`（`runtime.py`），模型可自主调用 `tool_memory_set(key, value, tags?)` / `tool_memory_get(key)` / `tool_memory_search(tag)` 记忆、回忆、按标签检索关键信息（对齐 opencode memory 语义）。记忆按 `conversation_id` 命名空间隔离，跨会话不可见；未注入记忆管理器时不注册工具。子 Agent（`code`/`web_search`）复用同一实例，主 Agent 记住的信息子 Agent 也可检索到。
534: 
535: **持久化优化**：`_persist_sync()` 保持"set 返回即落盘"的同步语义；另提供 `_persist_async_debounced()`（异步 `asyncio.to_thread` + 1 秒去抖窗口），用于高并发多 Agent 写共享记忆时避免阻塞各自事件循环（对齐 opencode 异步 storage 语义）。

539: ## 会话管理系统（Session Management）
540: 
541: 基于 SQLite（`backend/data/session.db`）的归一化会话体系，对齐 OpenCode 的 session 模型，为多 Agent 编排与任务执行提供统一底座。旧 `conversations.db` 保持只读，首次访问时惰性迁移（`conversation_id == session.id`），前端无需改动。
542: 
543: ### 核心概念
544: 
545: | 概念 | 说明 |
546: |------|------|
547: | **会话（Session）** | 用户/项目/工作区三级隔离；`parent_id` 构成子会话树（fork / 任务共享） |
548: | **消息日志** | `session_messages` append-only 事件日志，会话内自增 `seq` 水位 |
549: | **上下文纪元（Context Epoch）** | 每个会话持久化系统上下文快照 + `baseline_seq`，恢复/压缩后精确定位历史水位 |
550: | **压缩基线（Compaction Baseline）** | 压缩发生时落 `compaction` 消息 + 重建 epoch；checkpoint 作为 system 上下文带回，重启不丢摘要 |
551: | **撤销（Revert）** | 删除指定消息之后的所有消息与部件，并回滚纪元水位 |
552: 
553: ### 特性
554: 
555: - **per-session 串行 + 全局并发上限**：`service.write_lock(session_id)` 保证同一会话串行；`_agent_semaphore`（`app/api/chat.py`）受 `MAX_CONCURRENT_AGENTS` 全局限流（超出自动排队，SSE 发 `queued` 事件）
556: - **fork**：在任意消息处克隆子会话，独立消息日志与上下文，与父会话互不污染
557: - **级联删除 / 取消**：删除或打断会话时级联其子会话，并取消对应的 AgentBus 后台任务（`task_bridge.cancel_children`）
558: - **多 Agent 任务**：`/api/chat/multi-agent` 与 `/stream` 把每次任务登记为 `kind='task'` 子会话，父/子消息同步回写
559: - **压缩基线持久化**：历史超阈值被摘要/截断时落 `compaction` 消息 + 置 `time_compacted`；`history.load` 始终带回最新 checkpoint

584: ## 会话隔离（Session Isolation）
585: 
586: 前端采用**按会话隔离**的消息存储架构，确保切换历史会话时消息互不干扰：
587: 
588: ### 数据结构
589: 
590: ```typescript
591: // 每个会话独立存储
592: const sessions = ref<Record<string, SessionState>>({
593:   'session-id-1': {
594:     messages: [...],
595:     conversationId: 'conv-123',
596:     conversationTitle: '第一章讲了什么...',
597:     currentSteps: [],
598:     loading: false,
599:     abortController: null,
600:     streamPhase: 'running',   // 'idle' | 'queued' | 'running'
601:     queuePosition: null,       // 排队位置，null 表示不在排队
602:   },
603:   'session-id-2': { ... }
604: })
605: 
606: // 当前活跃会话
607: const activeSessionId = ref<string | undefined>(undefined)
608: ```
609: 
610: ### 核心优势
611: 
612: | 特性 | 说明 |
613: |------|------|
614: | **消息隔离** | 切换会话时，每个会话显示自己的消息列表 |
615: | **后台请求** | 流式请求在后台继续运行，完成时消息保存到对应会话 |
616: | **状态独立** | 每个会话有自己的 loading、currentSteps、streamPhase 状态 |
617: | **即时切换** | 已加载的会话切换时无需重新请求服务器，本地消息完整保留 |
618: | **内容不丢失** | 切换会话时，正在 streaming 的消息保留在本地，切回时立即可见 |
619: 
620: ### 双重持久化（IndexedDB + 服务器）
621: 
622: 解决 SSE 中断/页面刷新时消息丢失的问题：
623: 
624: ```
625: 发送消息
626:   │
627:   ├─ 1. 立即写入 IndexedDB（防 SSE 中断丢失 user 消息）
628:   ├─ 2. SSE 流式接收 → 消息在前端内存中累积
629:   ├─ 3. done 事件 → 写入 assistant 消息
630:   │     ├─ 写入 IndexedDB（本地缓存）
631:   │     └─ 后端写入 SQLite（持久化，含 sources/steps）
632:   │
633:   ▼
634: 切换会话 → loadConversation()
635:   │
636:   ├─ 始终从服务器获取最新数据（不再跳过）
637:   ├─ 从 IndexedDB 加载本地缓存
638:   └─ 合并策略：
639:        ├─ 服务器有、缓存没有 → 用服务器数据
640:        ├─ 缓存有、服务器没有 → 补入（SSE 中断时的 user 消息）
641:        └─ 两端都有 → 取 content 更长或有 sources/steps 的版本
642: ```
643: 
644: **解决的场景：**
645: 
646: | 场景 | 旧行为 | 新行为 |
647: |------|--------|--------|
648: | SSE 中途断开 | user 消息丢失，assistant 为空 | IndexedDB 保留 user 消息，下次加载时从服务器合并 |
649: | 页面刷新 | 内存清空，服务器 assistant 为空 | 从 IndexedDB 恢复 + 服务器合并 |
650: | 切换会话再切回 | 有时消息丢失 | 始终从服务器同步，合并本地缓存 |
651: 
652: 实现路径：
653: - 缓存层：`frontend/src/api/session-cache.ts` — IndexedDB CRUD + 合并逻辑
654: - Store 集成：`frontend/src/stores/multiAgent.ts` — `loadConversation()` / `persistSession()`
655: - 后端持久化：`backend/app/api/chat.py` — `_persist_multi_agent()` 在 `done`/`error` 事件时保存 `sources`/`steps`/`agents`/`tokens` 到 SQLite（主会话 + task 子会话）
656: 
657: ### 工作流程
658: 
659: ```
660: 用户在会话A发送消息
661:     │
662:     ├─ 创建 AbortController (key: session-A)
663:     ├─ streamPhase = 'queued' → 等待并发 slot
664:     ├─ 收到执行事件 → streamPhase = 'running'
665:     ├─ 开始流式接收
666:     │
667:     ▼
668: 用户切换到会话B
669:     │
670:     ├─ activeSessionId = B
671:     ├─ 会话A的本地消息保留（不从服务器覆盖）
672:     ├─ 显示会话B的消息
673:     └─ 会话A的流式请求继续在后台运行
674:          │
675:          ▼
676:     会话A请求完成
677:          │
678:          ├─ streamPhase = 'idle'
679:          ├─ 消息保存到 sessions['session-A'].messages

686: ### 并发控制
687: 
688: 后端使用全局信号量（`_agent_semaphore`，`settings.max_concurrent_agents` 默认 4）限制同时运行的 Agent 任务数，防止多会话同时 streaming 导致资源争抢。多 Agent 请求经 `/api/chat/multi-agent` 与 `/stream` 进入队列，同一会话内仍严格串行执行（`service.write_lock`）：
689: 
690: ```
691: Session A 发消息 → 获取 slot #1 → 开始执行
692: Session B 发消息 → 获取 slot #2 → 开始执行
693: Session C 发消息 → slot 已满 → 排队等待
694:     │
695:     ├─ SSE 事件: {type: "queued", queue_position: 1}
696:     ├─ Sidebar 显示 "⏳ #1"
697:     ├─ MultiAgentView Header 显示 "排队中 #1"
698:     │
699:     ▼
700: Session A 完成 → slot #1 释放 → Session C 获得 slot
701:     │
702:     ├─ SSE 事件: {type: "routing"} → 进入 running 阶段
703:     ├─ Sidebar 显示 "● streaming"
704:     └─ 开始流式输出
705: ```
706: 
707: | 配置 | 默认值 | 说明 |
708: |------|--------|------|
709: | `MAX_CONCURRENT_AGENTS` | 4 | 同时运行的最大 Agent 任务数 |
710: 
711: **session.db 连接池**：`app/session/db.py` 的 `_ConnectionPool` 维持固定连接（池大小 = `max(6, max_concurrent_agents + 2)`），`_get_db()` 借出、`close()` 归还；WAL 模式 + `busy_timeout=10000` 保证并发写安全。非默认路径的 DB 连接绕过池。
712: 
713: > 旧的状态 API `GET /api/chat/stream/status`（单 Agent 时期）已随单 Agent 模式移除；排队状态现在由 SSE `queued` 事件 + `queue_position` 承载，前端 `streamPhase` 跟踪。

723: ## 错误重试机制（Error Retry）
724: 
725: 参考 OpenCode 的重试架构，实现三层重试机制，覆盖 LLM API 故障、网络中断、SSE 断连等场景：
726: 
727: ### 三层重试架构
728: 
729: ```
730: ┌─────────────────────────────────────────────────────┐
731: │                    前端层                             │
732: │  SSE 断连检测 + 重试按钮 + 自动重试倒计时(5s×2次)     │
733: └──────────────────────┬──────────────────────────────┘
734:                        │ SSE error / 断连
735: ┌──────────────────────▼──────────────────────────────┐
736: │                   API 层                             │
737: │  错误分类(retryable/non-retryable) + 用户提示        │
738: └──────────────────────┬──────────────────────────────┘
739:                        │ 429/500/503
740: ┌──────────────────────▼──────────────────────────────┐
741: │                 后端层                                │
742: │  litellm num_retries=2 + AgentBus 事件循环自愈(5次)  │
743: └─────────────────────────────────────────────────────┘
744: ```
745: 
746: ### 错误分类
747: 
748: | 错误类型 | 分类依据 | 可重试 | 后端重试 | 前端自动重试 |
749: |----------|----------|--------|----------|-------------|
750: | 429 Rate Limit | `RateLimitError` / `429` | ✅ | litellm 2次 + AgentBus 5次 | 5s 倒计时，最多 2 次 |
751: | 500/502/503 | `InternalServerError` / `5xx` | ✅ | litellm 2次 + AgentBus 5次 | 5s 倒计时，最多 2 次 |
752: | 网络断开 | `Failed to fetch` / SSE 断连 | ✅ | — | 5s 倒计时，最多 2 次 |
753: | 超时 | `timeout` / `timed out` | ✅ | litellm 2次 | 5s 倒计时，最多 2 次 |
754: | Context Overflow | `context_length_exceeded` | ❌ | — | — |
755: | 401/403 | 认证失败 | ❌ | — | — |
756: | 用户取消 | `AbortError` | ❌ | — | — |
757: 
758: ### 退避策略
759: 
760: ```
761: retryAfter header → 使用 header 值（上限 60s）
762: 无 header → litellm 递增间隔；AgentBus 崩溃自愈按重试次数递增延迟（1s→5s）
763: 最大重试次数: AgentBus 事件循环 5 次
764: ```
765: 
766: ### 重试流程
767: 
768: ```
769: LLM API 报错 (429/500)
770:   │
771:   ├─ 1. litellm num_retries=2（自动，~1s/2s 间隔）
772:   │
773:   ├─ 2. AgentBus 事件循环崩溃自愈（最多 5 次，按重试次数递增延迟）
774:   │     └─ 每次重试推送 step 事件 → 前端显示 "重试中..."
775:   │
776:   └─ 3. 如果仍然失败 → SSE error 事件（retryable=true）
777:         │
778:         ├─ 前端显示红色错误消息 + ⚠️ 图标 + 重试按钮
779:         │
780:         └─ 自动重试倒计时（5s）
781:               ├─ 倒计时结束 → 自动重新发送
782:               ├─ 用户点击"取消" → 停止自动重试
783:               └─ 超过 2 次 → 停止自动重试，只保留手动重试按钮
784: ```
785: 
786: ### SSE 断连检测
787: 
788: 前端 `sendMessageStream()` 追踪是否收到 `done`/`error` 终端事件：
789: - 收到终端事件 → 正常结束
790: - 未收到终端事件就断开 → 抛出 `network` 类型错误，触发重试
791: 
792: ### 前端 UI
793: 
794: - **错误消息**：红色边框 + ⚠️ 图标，区别于正常 assistant 消息
795: - **重试按钮**：仅对 `retryable=true` 的错误显示
796: - **自动重试横幅**：底部显示倒计时 + 取消按钮
797: 
798: 实现路径：
799: - 后端重试：`backend/app/agent/graph.py` — `_llm_call()` num_retries
800: - 后端自愈：`backend/app/agent/bus.py` — `run_agent()` 事件循环崩溃重启（递增延迟，最多 5 次）
801: - 后端分类：`backend/app/api/chat.py` — SSE error 事件携带 retryable/statusCode
802: - 前端分类：`frontend/src/api/multiAgent.ts` / `frontend/src/stores/multiAgent.ts` — `classifyNetworkError()` + SSE 断连检测
803: - 前端重试：`frontend/src/stores/multiAgent.ts` — `retryLastMessage()` / `manualRetry()` / `cancelAutoRetry()`（5s 自动倒计时，最多 2 次）
804: - 前端 UI：`frontend/src/views/MultiAgentView.vue` — 错误样式 + 重试按钮 + 倒计时徽标
