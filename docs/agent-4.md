跨模型工具调用：设计与实现规范
供 Agent 执行。核心结论：模型原生工具调用能力不可依赖，必须在 Harness 层做适配。原生支持走标准协议，不支持走提示词注入 + 文本解析回退。切换模型前必须把旧工具调用痕迹"文本化"，不让新模型看到它读不懂的格式。

一、问题本质
不同模型对工具调用的支持程度差异极大，不能假设"模型支持工具调用"这个前提成立：

模型类型	工具调用能力	典型问题
Claude / GPT / Gemini 主流模型	原生支持，但格式各异	tool_call 序列化协议不同，切换即炸
开源模型（DeepSeek-R1、Gemma 等）	多数不支持或支持不完整	无 tools 参数，或返回格式不可靠
部分兼容层	表面支持实际报错	400 错误、ID 对不齐、role 连续冲突
结论：Agent 框架必须自己兜底，不能依赖模型能力。

二、两条路径：原生适配 + 文本回退
2.1 路径 A：原生支持（优先）
模型原生支持工具调用时走标准协议，但需要格式归一化层。

LiteLLM 已做大部分工作：把 100+ 厂商的工具调用统一为 OpenAI 格式的 tool_calls，请求侧 tools 和 tool_choice 翻译为各厂商原生参数（如 Anthropic 的 tool_use → OpenAI 的 function_call）。

Harness 层需补：

历史消息归一化：跨模型切换时，旧历史的 tool_calls / tool_result 格式可能与新模型不兼容。发送给新模型前统一转换为目标格式。

流式检测：部分模型流式响应先输出解释性文本再输出 JSON。需缓冲策略，检测 {"name": 或 [{"name": 模式后抑制前置文本。

错误恢复：模型返回的 tool_call 参数可能不合法 JSON。捕获解析错误，将错误信息作为工具结果返回给模型，让它自行修正。

2.2 路径 B：文本回退（兜底）
模型不支持原生工具调用时，用提示词注入 + 定界符解析实现等效功能。

参考 AnyToolCall 的做法：

text
原始请求中的 tools 定义 → 注入系统提示词：

You have access to the following tools:
- web_search: 搜索互联网
  Parameters: {"query": "string", "limit": "integer"}

How to call tools:
ꊰ▸function_name◂ꊰ
ꊰ▹{"param": "value"}◃ꊰ
ᐊ龘ꆈ
定界符设计要点：使用生僻字组合（如 ꊰ▸ ◂ꊰ）而非 <<<TOOL_CALL>>>，冲突率极低。模型几乎不会在正常文本中输出这些字符。

响应解析：从模型文本响应中正则匹配定界符，提取函数名和参数，还原为标准的 tool_calls 格式。流式场景下需要增量解析器，在定界符闭合时触发工具调用。

ollama-tools 采用类似思路：对不支持工具调用的 Ollama 模型，通过在提示词中嵌入工具描述，从模型输出中解析出 ToolCall(name='get_current_weather', arguments={'location': 'Paris'})。

关键决策点：能力探测。发起调用前判断模型是否支持原生工具调用：

维护 supports_tools: boolean 的模型能力表（从 LiteLLM 的模型信息或手动配置获取）。

对未知模型，默认走回退路径（保守策略）。

回退路径始终可用，作为原生路径失败时的降级方案。

四、与 Agent Loop 的协同
Agent Loop 本质是：模型评估 → 决定调工具 → 执行 → 结果回馈 → 重复，直到模型输出无工具调用的文本。

这个循环与工具调用协议无关。模型无论用原生 tool_calls 还是文本定界符，对 Loop 来说都是"模型请求了某个工具，需要执行并回馈结果"。

Harness 需做：

统一输出格式：无论走哪条路径，Adapter 输出标准 { tool_calls: [{ name, arguments }] } 结构。Loop 不感知模型差异。

统一回馈格式：工具执行结果回填时按目标模型协议转换。原生支持则用 role: "tool" + tool_call_id；回退路径则转换为文本，用定界符包裹后作为 role: "user" 内容注入。

Hook 机制：在工具执行前后插入拦截点（类似 Claude Code 的 PreToolUse / PostToolUse）。这层与模型无关，用于权限校验、日志、结果清洗。

五、历史消息兼容性（切换模型的关键）
切换模型时，旧历史的工具调用格式可能让新模型无法理解。AnyToolCall 的处理方式值得参考：

原始格式	转换后
role: "tool"	role: "user" + 定界符包裹
assistant.tool_calls	纯文本 + 定界符
连续相同 role 消息	合并为单条
原则：发送给目标模型前，将历史中所有工具调用痕迹"文本化"或"归一化为目标模型支持的格式"。不要让新模型看到它无法解析的 tool_call_id 或 tool_use 块。

七、验收标准
项	标准
能力探测	未知模型默认走回退路径，不静默失败
统一输出	两条路径均输出标准 { tool_calls: [{ name, arguments }] }
Loop 无感知	Agent Loop 代码中不出现任何厂商特有的工具调用格式
切换兼容	模型 A 产生的工具调用历史，切换模型 B 后仍可被理解并继续对话
流式正确	回退路径定界符闭合时立即触发工具调用，不等整段响应结束
错误恢复	非法 JSON 参数不导致循环崩溃，模型能收到错误并重试
Hook 生效	工具执行前后拦截点可配置，与模型选择无关
八、一句话记忆
原生支持走 LiteLLM 归一化，不支持走提示词注入 + 定界符解析；Harness 层统一输出 {name, arguments}，Loop 不感知模型差异；切换模型前把旧工具调用"文本化"，不让新模型看到它读不懂的格式。
