## 一、背景与目标

本项目为「多智能体知识库 AI 助手」：后端提供多 Agent 协作（Supervisor + 子 Agent）、RAG 检索（向量 + BM25 + 章节库）、SSE 流式、工具系统；前端提供桌面端与移动端（≤768px）双轨界面。

经过代码与文档审查，项目功能完成度高，但存在**安全、数据一致性、并发、前端链路、架构可维护性、部署容错**六类短板，同时移动端界面在**视觉层级、品牌感、组件一致性**上与同类产品存在差距。

本计划的目标：

1. 消灭 P0 级安全与数据正确性风险（2~4 周）。
2. 完成数据一致性、并发与关键功能补全（2~3 个月）。
3. 重构架构、补测试、完善部署容错（3~6 个月）。
4. 同步完成移动端 UI 改版，达到「专业、统一、有品牌感」的视觉效果。

## 三、总体框架：PDCA（大环套小环）

每个大问题独立成一个小循环，整体形成持续改进机制：

- **P（Plan）**：填写问题描述、现状数据、SMART 目标、根因分析、解决方案、责任人、时间线、成功指标。
- **D（Do）**：小范围试点 → 记录观察 → 反馈 → 全量推广。
- **C（Check）**：用数据对比预期与实际差距，定位根因。
- **A（Act）**：有效方案标准化固化（写入开发规范）；无效方案调整策略；归档文档后启动下一轮。

> 每个优化项都对应一张「PDCA 卡片」（看板中维护），格式见附录 A。

**A+C 落地明细（C5 第一阶段）**：
- `budget.llm_call_budget()`（`usable × CONTEXT_SAFETY_RATIO`，默认 0.9）作为单次调用截断目标 → 预留 ≥10% 估算误差垫；`generate.py` 三处截断全部改用该预算。
- 估算自适应校准：`token_counter.update_token_correction`（EMA α=0.02，observed 钳制 [0.9,1.5]）由 `core._llm_call`/`_assemble_response` 用实际 `usage.pt` 逐次校准 → 消除对 DeepSeek 中文/代码的系统性低估。
- `bound_tool_output` 新增 `TOOL_OUTPUT_MAX_TOKENS`（默认 8K）按 token 逐次减半封顶，超限写盘+续读提示（32KB 字符中文≈48K token 单条过大的问题根治）。
- 方案 D 基础：`context/step_state.py` 步骤状态落盘（`.agents/steps/<seq>.md` + `latest.md`），`_generate` 每轮在会话工作目录写执行快照（续跑/接力恢复用）。
- **方案 D 摘要替换**：`_generate` 新增 `_step_summarize`——长任务（≥`STEP_SUMMARY_MIN_ROUNDS`，默认 3 轮）起，每 `STEP_SUMMARY_INTERVAL`（默认 2）轮用 **`HierarchicalSummarizationMiddleware`** 把旧轮次压成摘要，上下文只装 `[摘要 checkpoint + 最近 keep 条（覆盖刚完成一轮）+ 当前步]`，结构性抑制线性膨胀（区别于 compaction 的阈值触发）；摘要失败回退原列表不阻断。
- 回归：`tests/test_context_overrun.py` 14 例（预算、校准、输出封顶、STEP_STATE、_step_summarize 替换/失败回退、长任务小步接线）。
- **A+C 真实长任务验证**：`scripts/verify_long_task_context.py` 用真实 `_generate` 主循环模拟 20 轮工具循环（每轮大段中文输出，`MAX_CONTEXT_TOKENS=12000`、`TOOL_OUTPUT_MAX_TOKENS=2000` 放大）→ **全程任一发送消息估算峰值 9163/9900（93%），无越界**；STEP_STATE 0001~0008 随轮次落盘。真实 320K 配置下同理（budget=280K + 10% 安全垫 + 自适应校正）。
- **方案 E/F 多请求接力**：`app/agent/long_task.py` `LongTaskCoordinator`——规划器把长任务拆 ≤N 步（`LONG_TASK_MAX_STEPS`），**每步一个独立 fresh-context 请求**（`agent.invoke`，上下文只装 计划+已完成 STEP_STATE+该步指令），步间经 `step_state` 落盘衔接（断点续跑）；计划 ≤1 步自动回落普通单请求（零开销）。接入：code 子 Agent chat 动作在 `LONG_TASK_STEP_MODE=true` 时走接力。
- **真实 API 长任务冒烟（PASS）**：`backend/scripts/smoke_long_task_api.py` 用真实 DeepSeek 跑「建 calculator.py + test + pytest」三文件任务 → 计划 3 步、10 次真实调用、**pt 峰值 4038/320000（1.3%）、0 越界**；E 效果可见——step2/step3 首调 pt 重置 ~3.3-3.6K 而非随步骤累积；STEP_STATE 0001~0003 落盘，最终回答聚合各步结果。`LONG_TASK_STEP_MODE=true` 开启接力。
- 回归：`tests/test_context_overrun.py` 19 例（+协调器规划解析/单步回落/多步 fresh-context/STEP_STATE/接线开关）。

**诊断（为什么总超 MAX_CONTEXT_TOKENS）**：实测 `.env`：`MAX_CONTEXT_TOKENS=320000`、`CONTEXT_RESERVE_TOKENS=8192` → `usable_context_tokens()=311,808`，距硬上限仅 **2.7% 余量**。三处叠加顶穿：
1. **估算系统性低估**：`estimate_tokens`=tiktoken cl100k×1.13（P8 实测校准于轻量中英场景）；长任务里中文工具输出/代码经 DeepSeek tokenizer 膨胀常达 15–40% → 截断按「估算」放行、Provider 按「实际」拒绝/超限。
2. **全量重发式工具循环**：`_generate` 8 轮每轮整包重发「system+全历史+已执行轮次全部 tool 结果」，compaction 阈值 187K（usable 60%）才压缩、prune 40K 才回收 → 中间几十轮线性逼近上限，压缩/裁剪只把「已发生的事」塞摘要，**当前请求携带量仍单调膨胀**。
3. **单条不可切 + 工具输出过大**：`bound_tool_output` 200 行/32KB 字符，中文 32KB≈48K token 一条；`truncate_messages` 按消息粒度收、无法切单条 → `_ensure_within_budget` 常告警 `Compacted context still exceeds threshold`。

**设计：小步快走执行模式（三步实现，从低到高）**——原则：**上下文只装「当前步 + 已完成状态摘要」，不装「任务全程」**，把「单请求单上下文大循环」拆成「多步骤、每步独立小上下文」：
- **① 硬护栏（不改循环结构）**：每轮 LLM 前预算核对——`estimate(messages)+estimate(tools)+系统提示词` 超 `usable×SAFETY_RATIO`（建议 0.9，默认 0.75）则强制 compaction+prune，仍超则**本轮结束并输出「已完成+剩余任务」结构化小结**（复用 MAX_STEPS 收尾），绝不发越界请求；`TOKEN_ESTIMATE_CORRECTION` 改为按最近 N 次 `llm.usage.pt/估算` 实际比值滑动自适应；`bound_tool_output` 改按 token 截断（单条 ≤8K token，超限写盘+续读提示）。
- **② 步骤边界状态落盘（checkpoint-as-state，核心）**：每轮结束把「已完成工作+涉及文件路径+待办」写成结构化 STEP_STATE（对齐 COMPACTION_TEMPLATE Objective/Work State/Next Move）并落盘 `.agents/steps/<round>.md`（跨请求不丢）；下一轮消息 = `system + 最近一轮完整 + STEP_STATE 摘要 + 最新结果`，**旧原始轮次不再携带**——等价于把压缩阈值拉低到「每轮都压缩」，但锚定的是落盘文件状态（已完成事实）而非纯对话，摘要更可靠，上下文不再随轮次线性膨胀。
- **③ 多请求接力执行（默认长任务路径）**：检测到任务需 >N 步（或 `_decompose` 产多步骤）→ 接力模式：先生成 `## 实施计划` 步骤列表，**每步一个独立请求**（fresh context=system+计划+STEP_STATE+该步指令），步间只传落盘 STEP_STATE；复用现有 `tool_task`/code 子 Agent（fresh context）作为默认载体——主 Agent 只编排、把每步委派给子 Agent（`SUBAGENT_DEPTH=1`），主上下文永不膨胀；中断恢复经 session_tasks + STEP_STATE 文件从断点续跑。

**备选方案对比（评估过、未全部采用）**：

| 方案 | 思路 | 优点 | 缺点 | 取舍 |
|---|---|---|---|---|
| A · 硬护栏 | 每轮预算核对 + 估算自适应 + 工具输出按 token 截断 + 超限收尾 | 改动最小、当天可落地、杜绝越界 | 上下文仍随轮次膨胀（不解决慢） | ✅ **采用为全请求基线** |
| B · 激进压缩 | compaction 阈值 60%→25% 提前触发 | 改配置即可 | 摘要调用频繁（延迟/成本）、丢细节 | ❌ 否——摘要开销不值得 |
| C · 摘要+尾部调优 | 修正估算、压缩目标强制 ≤usable×0.5、单条输出封顶 | 不新增概念、风险最低 | 长任务仍携带尾部长轮次 | ✅ **并入 A**（估算自校准 + 输出封顶） |
| D · STEP_STATE 落盘 | 每轮写工作状态文件，下一轮只带摘要+当前步 | 上下文真不膨胀、可跨请求续跑 | 需提示词纪律、丢对话细节 | ✅ 采用（方案②） |
| E · 多请求接力 | 计划拆步骤、每步独立请求 | 每请求极小、可续跑可并行 | 需新编排循环、短任务反而慢 | ✅ 采用（方案③，长任务默认路径） |
| F · 子 Agent 委派 | tool_task 把每步委派给 code 子 Agent | 基建已就绪、主上下文永不膨胀 | 深度上限 1、结果回传仍累积 | ✅ 采用（E 的载体） |
| G · 前缀缓存 | 稳定前缀 → DeepSeek 缓存 0.1x 计费 | 降成本/延迟 | 不解决硬上限、与「每轮摘要替换」冲突 | ⏸ 配套项，缓存命中稳定后再评估 |

**推荐组合（分层，已定为 C5 实施路线）**：**A+C 为全请求基线**（硬护栏 + 估算自校准 + 输出封顶，根治「越界」）→ 长任务（预估 >N 步）**切 D/E/F 小步快走**（短任务保留 in-loop 快路径；长任务走慢路径多请求/委派，上下文永不膨胀）。
